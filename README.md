# open-meteo-mcp

MCP-сервер вокруг бесплатного API [Open-Meteo](https://open-meteo.com/): погода, прогноз, качество воздуха и геокодирование — как инструменты для ИИ-агента. Умеет сохранять выбранные данные о погоде локально и выгружать их в Excel-таблицу, которую агент возвращает файлом.

Сервер сразу спроектирован под выгрузку на VPS: два транспорта (stdio для локальной работы и Streamable HTTP для удалённого подключения), bearer-аутентификация, Docker/systemd/nginx-артефакты.

## Что реализовано

Три требования из задачи и то, как они закрыты:

| Требование | Реализация |
|---|---|
| **Регистрация инструмента** | `server.registerTool(name, config, handler)` в `src/tools/*.ts`; единая точка регистрации — `src/tools/index.ts`. Все 12 инструментов имеют `title`, `description` и `annotations` (`readOnlyHint`, `destructiveHint`). |
| **Описание входных параметров** | Схемы на Zod (`.describe()` на каждом поле) → SDK генерирует JSON Schema, которую видит модель. Проверяется тестом `documents every input parameter via the generated JSON Schema`. |
| **Возврат результата** | Каждый инструмент возвращает **одновременно** `content` (текст для модели) и `structuredContent` (типизированный JSON, валидируемый по `outputSchema`). |

Дополнительно, с прицелом на VPS:

- два транспорта — `stdio` и Streamable HTTP;
- stateless-режим по умолчанию (нет привязки к сессии → безопасны рестарты и горизонтальное масштабирование);
- bearer-аутентификация с сравнением за постоянное время;
- сервер **отказывается** слушать не-loopback адрес без токена;
- retry с экспоненциальным backoff, таймауты, типизированные ошибки;
- JSON-логи в stderr (stdout на stdio-транспорте занят протоколом);
- graceful shutdown по SIGTERM/SIGINT, `/healthz` для мониторинга;
- хранение сводок и выгрузка в Excel **без единой новой зависимости**: контейнер `.xlsx` (ZIP + OOXML) собирается своим кодом в `src/xlsx/`;
- Dockerfile (multi-stage, non-root), docker-compose, systemd unit, пример nginx.

## Требования

- **Node.js ≥ 20** (используется глобальный `fetch` и `AbortSignal.any`). Проверено на Node 26.
- Исходящий HTTPS к `ensemble-api.open-meteo.com` (погода), `geocoding-api.open-meteo.com` (геокодирование) и `air-quality-api.open-meteo.com` (качество воздуха).
- API-ключ **не нужен** — тариф Open-Meteo бесплатный.

## Источник данных

Погода берётся из Open-Meteo, но **не с классического хоста `api.open-meteo.com`**: его IP (`94.130.142.35`) недоступен с некоторых сетей — TCP-соединение просто уходит в таймаут, при этом все остальные хосты Open-Meteo отвечают нормально. Это проверено: DNS отдаёт корректный адрес (подтверждено через Cloudflare DoH), а контрольная загрузка файла на 928 КБ с другого хоста занимает 0,6 с — то есть дело не в сети целиком и не в коде.

Поэтому по умолчанию используется **`ensemble-api.open-meteo.com`**, который:

- отдаёт **ту же самую JSON-схему** — те же имена переменных, те же коды погоды WMO, те же единицы;
- доступен отовсюду;
- не требует ключа;
- даёт полный горизонт **16 суток** при `models=gfs05`.

Единственное отличие: в ансамблевом продукте нет `precipitation_probability`, поэтому это поле всегда `null`. В описании поля в схеме инструмента это указано явно, чтобы модель не приняла `null` за «осадков не будет».

### Два поддерживаемых режима

| | **A. Ансамблевый хост** (по умолчанию) | **B. Стандартный хост** (для VPS) |
|---|---|---|
| `OPEN_METEO_FORECAST_URL` | `https://ensemble-api.open-meteo.com` | `https://api.open-meteo.com` |
| `OPEN_METEO_FORECAST_PATH` | `/v1/ensemble` | `/v1/forecast` |
| `OPEN_METEO_MODELS` | `gfs05` | *(пусто)* |
| Горизонт прогноза | 16 суток | 16 суток |
| Вероятность осадков | ❌ `null` | ✅ есть |
| Доступность | отовсюду | зависит от сети |

Переключение на стандартный хост — это три переменные окружения, без правок кода:

```bash
export OPEN_METEO_FORECAST_URL=https://api.open-meteo.com
export OPEN_METEO_FORECAST_PATH=/v1/forecast
export OPEN_METEO_MODELS=          # пустое значение = не отправлять models вовсе
```

> **Почему `gfs05`.** Ансамблевый API требует явную модель и отклоняет `best_match`. Горизонт у моделей разный: `icon_seamless` и `icon_global` покрывают только 7 суток (дальше значения приходят `null`), `gfs025` — 10, `ecmwf_ifs025` — 14, и только `gfs05` даёт полные 16 суток вместе с УФ-индексом.

### Почему не wttr.in

Изначально рассматривался `https://wttr.in/api`, но:

1. **Такого эндпоинта не существует** — `/api` возвращает обычный текстовый отчёт для места с названием «api», а не JSON.
2. **Реальный JSON-эндпоинт `?format=j1` нерабочий.** Из 12 запросов (Москва, Лондон, Париж, Нью-Йорк, координаты; gzip и без; HTTP/1.1 и HTTP/2; таймауты до 150 с) **ни один** не вернул валидный JSON: ответ обрывается на 10665 или 13037 байт внутри блока `weatherIconUrl` и дальше висит. Это поведение самого wttr.in, а не сети — контрольная загрузка 928 КБ с GitHub проходит за 0,6 с.
3. Надёжно работают только текстовые форматы, а это означает отказ от прогноза, качества воздуха и геокодирования.

Если нужен независимый поставщик, проверенным запасным вариантом остаётся **MET Norway** (`api.met.no`, бесплатно, без ключа, глобально, ~10 суток): он тоже доступен с этой машины, но требует заголовок `User-Agent` (без него — 403) и отдаёт собственные коды символов вместо WMO. В текущей реализации он не подключён.

## Инструменты

### `geocode_location`

Превращает название места в координаты и метаданные.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `name` | string | да | Название места: `Moscow`, `Санкт-Петербург`. Без индекса и страны. |
| `count` | int 1–20 | нет | Сколько кандидатов вернуть. По умолчанию 5. |
| `language` | string | нет | ISO-639 код языка названий (`en`, `ru`). По умолчанию `en`. |
| `countryCode` | string(2) | нет | ISO-3166-1 alpha-2 для сужения поиска (`RU`, `US`). |

Возвращает координаты, страну, регион, таймзону, население и флаг `ambiguous` — он помогает агенту понять, что название неоднозначно («Springfield»).

### `get_current_weather`

Текущая погода: температура, «ощущается как», влажность, осадки, облачность, давление, ветер (скорость/направление/порывы), а также расшифрованный код погоды WMO.

Общие параметры локации (см. ниже) + `units`.

### `get_weather_forecast`

Прогноз по дням до 16 суток: min/max температура, «ощущается», сумма осадков, снег, УФ-индекс, восход/закат, максимум ветра. Опционально — почасовой ряд. Вероятность осадков зависит от источника данных (см. [Источник данных](#источник-данных)).

Общие параметры локации + `units`, плюс:

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `days` | int 1–16 | нет | Число дней прогноза. По умолчанию 7. |
| `include_hourly` | bool | нет | Добавить почасовой ряд (ответ вырастает ~24×). По умолчанию false. |

### `get_air_quality`

Качество воздуха: PM2.5, PM10, O₃, NO₂, SO₂, CO, аммиак, пыль, УФ-индекс, европейский и американский индексы AQI, плюс расшифрованная категория опасности и рекомендация для здоровья.

Общие параметры локации.

### Инструменты периодического сбора

Пять инструментов вокруг фонового сборщика — см. [Периодический сбор погоды](#периодический-сбор-погоды).

| Инструмент | Назначение |
|---|---|
| `start_weather_watch` | Зарегистрировать локацию для сбора каждые 15 минут. |
| `stop_weather_watch` | **Пауза**: перестать опрашивать, история сохраняется. Обратимо. |
| `delete_weather_watch` | Удалить watch вместе с историей. Необратимо, требует `confirm: true`. |
| `list_weather_watches` | Показать активные watch-и и здоровье сбора. |
| `get_weather_watch_report` | Агрегированный отчёт за окно времени. |

### Инструменты сохранения сводок и выгрузки в Excel

Три инструмента вокруг локального хранилища «сводок» — см. [отдельный раздел](#сохранение-сводок-и-выгрузка-в-excel).

| Инструмент | Назначение |
|---|---|
| `save_weather_summary` | Сложить таблицу погодных значений (и свой текстовый анализ) в JSON на диске сервера. Данные не запрашивает — сохраняет то, что передал агент, либо агрегат уже собранного `watch`. |
| `list_weather_summaries` | Показать, что уже сохранено: id, заголовок, строки, места, период, источник. По `dataset_id` — детали, по `include_entries` — сами строки. |
| `export_weather_summary_excel` | Собрать из сохранённой сводки `.xlsx` (листы `Weather`, `Stats`, `Info`), записать файл на сервер и **вернуть его** во вложении-ресурсе (base64) вместе с путём, размером и SHA-256. |

### Общие параметры локации

Все три «погодных» инструмента принимают локацию **любым из двух способов** — это сделано специально, чтобы типовой запрос укладывался в один вызов инструмента:

| Параметр | Тип | Описание |
|---|---|---|
| `latitude` | number −90…90 | Широта. Указывать вместе с `longitude`. |
| `longitude` | number −180…180 | Долгота. Указывать вместе с `latitude`. |
| `location` | string | Название места — сервер сам его геокодирует и берёт самый населённый вариант. |
| `countryCode` | string(2) | Сужает геокодирование `location`. |
| `language` | string | Язык названия места. По умолчанию `en`. |
| `units` | `metric` \| `imperial` | Система единиц. По умолчанию `metric`. |

> Почему «или/или» не выражено в JSON Schema: MCP-клиенты показывают модели упрощённую JSON Schema, в которой взаимоисключение не выражается. Поэтому правило проверяется в коде, а ошибка возвращается **как текст с указанием, что именно исправить** — так модель самокорректируется, а не получает невнятный отказ.

## Периодический сбор погоды

Фоновый сборщик опрашивает погоду **каждые 15 минут**, складывает показания в JSON и умеет отдавать агрегированный результат за окно времени.

### Зачем это отдельно от `get_current_weather`

`get_current_weather` отвечает на вопрос «какая погода сейчас» — один вызов, один ответ. Сборщик отвечает на «что происходило с погодой последние сутки»: он работает, пока его никто не спрашивает, и накапливает историю, которую потом можно усреднить.

### Как это устроено

```
start_weather_watch ──► реестр watch-ей (data/watches.json)
                              │
                    таймер процесса, каждые 15 мин
                              │
                              ▼
                    опрос погоды ──► data/samples/<id>.json
                              │
                              ▼
              get_weather_watch_report ──► min/max/avg, тренд, осадки, условия
```

**Ключевая деталь реализации.** Сервер работает в stateless-режиме MCP, где на **каждый HTTP-запрос создаётся новый объект сервера**. Поэтому таймер нельзя запускать при регистрации инструмента — он создавался и уничтожался бы на каждом вызове и никогда не срабатывал бы по расписанию. Сборщик живёт на уровне процесса (создаётся один раз в `buildDeps`, запускается из точки входа), а накопленные данные лежат в файле, а не в памяти. Это же даёт сохранность истории при перезапуске контейнера.

### Что попадает в отчёт

| Группа | Содержимое |
|---|---|
| Температура | min, max, среднее, изменение и **тренд** (сравнение старой половины окна с новой) |
| Ощущаемая | то же |
| Осадки | сумма, максимум за сэмпл, число сэмплов с осадками |
| Ветер | среднее, максимум, сильнейший порыв |
| Давление / влажность | min, max, среднее, тренд |
| Условия | как часто встречалось каждое, доля в процентах, доминирующее |
| Здоровье сбора | сколько сэмплов, фактический период наблюдения, отставание, последняя ошибка |

Тренд считается по средним двух половин окна, а не по первой и последней точке: крайние значения — одиночные измерения, и один выброс иначе разворачивал бы направление.

### Файлы на диске

```
data/
├── watches.json              реестр watch-ей и статистика сбора
└── samples/
    ├── moskva.json           168 часов истории по умолчанию
    └── sankt-peterburg.json
```

Запись атомарная: данные пишутся во временный файл и переименовываются поверх целевого, поэтому падение в момент записи не оставит обрезанный JSON.

**Про временные метки.** В каждом сэмпле два времени:

| Поле | Смысл | Формат |
|---|---|---|
| `at` | когда **этот сервер** снял показание — по нему работают окно и retention | `2026-09-25T18:02:39.191Z` (UTC) |
| `observed_at` | метка **провайдера** для самих значений | `2026-09-25T23:00+05:00` |

Оба содержат дату. `observed_at` намеренно хранится со **смещением таймзоны**: провайдер отдаёт «голое» настенное время вида `2026-09-25T23:00`, которое при чтении как UTC дало бы ошибку в 5 часов для Екатеринбурга. Смещение берётся из ответа API и подставляется автоматически; сэмплы, записанные до появления этого поля, исправляются при загрузке с диска — настенное время сохраняется, убирается только неоднозначность.

Посмотреть вручную на VPS:

```bash
cd /opt/open-meteo-mcp
python3 -m json.tool data/samples/moskva.json | head -40
# или последнее показание:
python3 -c "import json; print(json.load(open('data/samples/moskva.json'))['samples'][-1])"
```

### Как работает окно `window_hours`

Окно — это **фильтр по времени сбора**, а не требование иметь столько данных. Отбираются сэмплы, у которых `at` (момент сбора) не старше `now − window_hours`. Никакого минимума данных нет.

Поэтому запрос за 24 часа на watch-е, который живёт 10 минут, **успешно вернёт эти 10 минут**. Это сделано намеренно: иначе первый сутки после регистрации watch отчёт был бы бесполезен, а агент не понимал бы, работает ли сбор вообще.

Честность обеспечивается тремя полями, которые надо смотреть вместе:

| Поле | Что показывает |
|---|---|
| `sample_count` | Сколько сэмплов попало в окно — **все, что есть** |
| `observed_span_minutes` | Сколько минут реально покрывают эти сэмплы |
| `first_sample_at` / `last_sample_at` | Границы наблюдённого периода |
| `staleness_minutes` | Насколько свежий последний сэмпл |

Пример реального ответа через 51 минуту после регистрации watch:

```
generated at: 2026-09-25T18:34:41.249Z (UTC) = 2026-09-25 23:34:41 local (Asia/Yekaterinburg)
samples: 10 sample(s) in the window, covering 51.2 min of the requested 24 h
window: 2026-09-25T17:34:24.949Z .. 2026-09-25T18:25:35.327Z (UTC)
```

**Чего здесь намеренно НЕТ: квоты.** Раньше отчёт показывал `expected_samples` (сколько сэмплов было бы при полном покрытии) и `coverage_percent` — как «сигнал достоверности». На практике это сломало работу: агент прочитал «7 из 96» не как «столько успело накопиться», а как «данных не хватает, отвечать нельзя», и отказался строить суточную сводку, хотя у него на руках были все имеющиеся записи.

Процент от квоты читается моделью как порог прохождения. Продолжительность наблюдения передаёт тот же факт, не порождая квоты, которую можно «не сдать».

**Агрегаты считаются по тому, что есть.** `min`/`max`/`avg` — по имеющимся сэмплам. `trend` при одном сэмпле возвращает `unknown` (сравнивать не с чем), при двух и более — сравнение половин окна.

**Пустое окно и пустой watch — разные вещи.** Если история есть, но лежит за пределами окна (например, `window_hours: 1`, а последний сэмпл был 10 часов назад), отчёт скажет об этом прямо и подскажет увеличить окно, вместо неверного «данных ещё нет». Оба случая покрыты тестами.

### Пауза и удаление — разные операции

Это сознательное разделение: **остановка сбора не удаляет историю.**

| | `stop_weather_watch` | `delete_weather_watch` |
|---|---|---|
| Прекращает опрос | да | да |
| Сохраняет накопленные сэмплы | **да** | нет |
| Обратимо | да — `start_weather_watch` с тем же id возобновляет сбор, история продолжается | **нет** |
| Аннотация для агента | `destructiveHint: false` | `destructiveHint: true` |
| Доп. защита | — | обязательный `confirm: true` |

Почему так: пауза — рутинное действие, а потеря истории необратима. Если бы остановка удаляла данные, случайный вызов агента стирал бы то, что копилось днями. Поэтому удаление вынесено в отдельный инструмент с явным подтверждением — модель не вызовет его «заодно».

Пока watch на паузе, `get_weather_watch_report` продолжает работать по накопленной истории и явно помечает отчёт:

```
NOTE: this watch is PAUSED — no new samples are being collected. Its stored history is intact.
Resume it with start_weather_watch (id: "ekaterinburg") when you need live data again.
```

Это важно: без такой пометки растущее `staleness_minutes` выглядело бы как сбой сбора, и агент пошёл бы чинить несуществующую проблему.

### Идентификаторы и защита от дублей

Если не передать `id`, он выводится из названия места: `Москва` → `moskva` (кириллица транслитерируется), координаты → `point-59_94-30_31`.

**Повторный вызов для той же точки не создаёт дубль.** Если координаты уже отслеживаются, `start_weather_watch` возвращает существующий watch, а не заводит `moskva-2`:

```
This location is already tracked as "ekaterinburg" — reusing that watch instead of creating a duplicate.
```

В `structuredContent` это видно по полю `reused_existing_location: true`, а `created_at` остаётся исходным — это не пересоздание. Если watch был на паузе, такой вызов его возобновляет.

Зачем: без дедупликации каждый вызов без `id` плодил новый watch на ту же точку, и каждый из них опрашивал одно и то же место — то есть один и тот же запрос уходил в Open-Meteo дважды, трижды и так далее.

Координаты сравниваются с округлением до 4 знаков (~11 м): геокодирование возвращает одинаковые значения для одного места, поэтому реальные дубли ловятся, а два намеренно разных близких объекта остаются разными watch-ами.

**Явный `id` отключает дедупликацию** — это осознанный запрос на отдельный watch даже в той же точке.

### Важно для развёртывания

Контейнер запущен с `read_only: true`, поэтому **каталогу данных нужен примонтированный volume** — он уже прописан в `docker-compose.yml` (`./data:/app/data`), а каталог на хосте должен принадлежать uid 1000 (пользователь `node` в контейнере):

```bash
cd /opt/open-meteo-mcp
sudo mkdir -p data && sudo chown 1000:1000 data
```

Если каталог недоступен для записи, сервер **не падает**: сборщик отключается, `/healthz` показывает `watcher.available: false`, а инструменты watch возвращают понятную ошибку с указанием, что примонтировать. Молча собирать пустоту он не будет.

### Проверка, что сбор работает

```bash
curl -s http://127.0.0.1:3000/healthz | python3 -m json.tool   # блок watcher
```

В ответе `watcher.watchCount`, `watcher.failingWatches` и `watcher.intervalSeconds`. Если `failingWatches` не пуст, отчёт по этим watch-ам покажет предупреждение и текст последней ошибки — устаревшие данные не будут молча усреднены.

## Сохранение сводок и выгрузка в Excel

Два инструмента превращают разрозненные ответы о погоде в файл, который можно открыть в Excel:

1. **`save_weather_summary`** — складывает таблицу значений **локально**: JSON-файл на диске сервера;
2. **`export_weather_summary_excel`** — собирает из сохранённой таблицы настоящий `.xlsx` и возвращает файл.

Третий, служебный — **`list_weather_summaries`**: по нему агент узнаёт `dataset_id` (угадать его нельзя, а помнить между сессиями — тем более).

### Зачем это отдельно от `watch`

| | Периодический сбор (`watch`) | Сохранённая сводка (`summary`) |
|---|---|---|
| Кто выбирает данные | сервер по таймеру | агент: города, даты, метрики |
| Что хранится | сырые показания каждые 15 минут | строки «место + дата» и текстовый анализ агента |
| Срок жизни | обрезается по `WATCH_RETENTION_HOURS` | не истекает |
| Выход | агрегат за окно времени | файл `.xlsx` |

Типовой сценарий: агент смотрит погоду в нескольких городах, сравнивает, складывает результат в сводку и отдаёт пользователю таблицу — вместо того чтобы вставлять таблицу текстом в чат.

### `save_weather_summary`

Что передавать: `entries` — по одному объекту на «место + дата». Все поля-метрики необязательны: в таблицу попадут только те столбцы, где есть данные.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `title` | string | нет | Заголовок сводки. Из него выводится `dataset_id`. |
| `dataset_id` | string | нет | Явный id (`[A-Za-z0-9_-]`). Тот же id с `replace: true` обновляет сводку. |
| `summary` | string | нет | **Ваш текстовый анализ** — хранится вместе с данными и целиком печатается на листе `Info`. |
| `source` | string | нет | Происхождение данных, например `get_weather_forecast (ensemble gfs05)`. |
| `tags` | string[] | нет | Метки для поиска. |
| `units` | `metric` \| `imperial` | нет | Система единиц; подставляется в заголовки столбцов. |
| `replace` | bool | нет | Перезаписать существующую сводку с тем же id. По умолчанию `false` — сохранение отклоняется с указанием, какой id уже занят. |
| `entries` | object[] | нет\* | Строки данных. |
| `location`, `country`, `latitude`, `longitude`, `date` | — | нет | Значения по умолчанию для строк, где их нет. Удобно для «один город, много дней». |
| `watch_id` | string | нет\* | Вместо `entries`: сохранить историю, собранную фоновым сборщиком. |
| `watch_window_hours` | int 1–8760 | нет | Окно сбора для режима `watch_id`. По умолчанию 24. |

\* Нужно ровно одно из двух: `entries` или `watch_id`.

Поля строки: `location`, `country`, `latitude`, `longitude`, `date`, `condition`, `weather_code`, метрики `temperature`, `apparent_temperature`, `temperature_min`, `temperature_max`, `relative_humidity`, `precipitation`, `precipitation_probability`, `snowfall`, `cloud_cover`, `pressure_msl`, `wind_speed`, `wind_direction`, `wind_gusts`, `uv_index`, а также `note` и `extra` (любые скалярные пары → отдельные столбцы).

**Как переносить данные из других инструментов.** Для `get_current_weather` имена совпадают один в один (`temperature`, `apparent_temperature`, `relative_humidity`, `precipitation`, `cloud_cover`, `pressure_msl`, `wind_speed`, `wind_direction`, `wind_gusts`, `condition_en` → `condition`, `weather_code`). У дневного прогноза upstream-имена длиннее, поэтому:

| Из `get_weather_forecast` (элемент `days[]`) | Поле строки |
|---|---|
| `date` | `date` |
| `temperature_min`, `temperature_max` | `temperature_min`, `temperature_max` |
| `apparent_temperature_max` (или `_min`) | `apparent_temperature` |
| `precipitation_sum` | `precipitation` |
| `snowfall_sum` | `snowfall` |
| `precipitation_probability_max` | `precipitation_probability` |
| `wind_speed_max` | `wind_speed` |
| `wind_gusts_max` | `wind_gusts` |
| `wind_direction_dominant` | `wind_direction` |
| `uv_index_max` | `uv_index` |
| `condition_en` (или `condition_ru`) | `condition` |
| `sunrise`, `sunset`, `daylight_duration` | в `extra` (или в `note`) |

Значения из `get_air_quality` кладите в `extra`, например `{"pm2_5": 12.4, "european_aqi": 42}` — каждый ключ станет отдельным столбцом.

### Сохранение из `watch`

Если погода уже собирается фоновым сборщиком, отдельный поиск не нужен:

```jsonc
{ "watch_id": "ekaterinburg", "watch_window_hours": 24, "summary": "За сутки температура падала..." }
```

Инструмент возьмёт историю watch и **свернёт её в одну строку на сутки**: средняя, минимальная и максимальная температура за день, сумма осадков, максимум ветра и порывов, средняя влажность и давление, доминирующее условие. Это не то же самое, что дневной прогноз: `temp_min`/`temp_max` здесь — крайние **измеренные** значения, о чём строка прямо пишет в `note`. Направление ветра берётся у самого сильного измерения, а не средним: среднее 350° и 10° — это 180°, то есть противоположность истине.

### `export_weather_summary_excel`

```jsonc
{ "dataset_id": "pogoda-v-moskve", "file_name": "weather-moscow", "include_file_content": true }
```

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `dataset_id` | string | да | id сохранённой сводки. |
| `file_name` | string | нет | Базовое имя файла без пути и без `.xlsx`. id датасета добавляется префиксом. |
| `include_file_content` | bool | нет | Вложить книгу в ответ как base64. По умолчанию `true`. |

В ответе: `file_path` (абсолютный путь на сервере), `file_uri`, `bytes`, `sha256`, `rows`, `columns`, `sheets`, `content_included`.

**Как именно возвращается файл.** В `content` ответа, кроме текстового блока, лежит встроенный ресурс:

```jsonc
{
  "type": "resource",
  "resource": {
    "uri": "file:///app/data/summaries/exports/pogoda-v-moskve.xlsx",
    "mimeType": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
    "blob": "<base64>"
  }
}
```

Это принципиально для удалённого (HTTP) подключения: файловая система VPS агенту недоступна, и путь сам по себе ничего не даёт — файл приходит в самом ответе. Порог встраивания — `SUMMARY_MAX_INLINE_BYTES` (по умолчанию 8 МиБ): более крупная книга всё равно записывается на диск, но в ответе вместо base64 будет путь и причина (`content_omitted_reason`).

### Что внутри книги

| Лист | Содержимое |
|---|---|
| `Weather` | по строке на каждую запись сводки. Столбцы — только те, где есть данные; единицы указаны в заголовке (`temperature, °C`). Шапка закреплена, включён автофильтр, ширины столбцов подобраны. |
| `Stats` | min/max/среднее по каждому месту и метрике, а для осадков и снега ещё и сумма. Для направления ветра среднее намеренно пустое. |
| `Info` | id, заголовок, **полный текст анализа**, источник, единицы, метки, места, период, время сохранения и генерации, путь к JSON-файлу данных, а также пояснение, что пустая ячейка означает «источник не дал значение». |

Даты пишутся текстом в формате `YYYY-MM-DD`: так они не могут быть переинтерпретированы другой таймзоной при открытии и при этом корректно сортируются.

### Файлы на диске

```
data/
├── watches.json                      реестр watch-ей
├── samples/                          история сбора
└── summaries/                        сохранённые сводки
    ├── index.json                    метаданные всех сводок (перестраивается при потере)
    ├── pogoda-v-moskve.json          сама сводка: метаданные + строки
    └── exports/
        ├── pogoda-v-moskve-2026-09-26_04-52-40.xlsx
        └── pogoda-v-moskve-weather-moscow.xlsx
```

`index.json` — только кэш для быстрого листинга: если его удалить или испортить, он пересобирается из файлов сводок при первом обращении. Файлы в `exports/` сверх `SUMMARY_MAX_EXPORTS` (по умолчанию 10) на один датасет обрезаются при каждой новой выгрузке; файл, который возвращается в текущем ответе, не удаляется никогда.

Отдельного инструмента удаления сводки нет: перезапишите её через `replace: true` либо удалите JSON-файл на хосте (например `rm data/summaries/old.json`).

### Ограничения выгрузки

- Книга собирается собственным генератором (`src/xlsx/`): значения, ширины, закреплённая шапка, автофильтр, числовые форматы. Формул, диаграмм, сводных таблиц, объединённых ячеек и условного форматирования нет.
- Ограничения объёма: до `SUMMARY_MAX_ENTRIES` строк в сводке (5000) и до `SUMMARY_MAX_DATASETS` сводок (200).
- Пустая ячейка означает «источник не дал значение», а не ноль.

## Как возвращается результат

Ответ каждого инструмента содержит два канала:

```jsonc
{
  "content": [
    { "type": "text", "text": "Current weather in Москва, Россия (55.75204, 37.61781)\n..." }
  ],
  "structuredContent": {
    "location": { "name": "Москва", "latitude": 55.75204, "longitude": 37.61781, "timezone": "Europe/Moscow" },
    "observed_at": "2026-09-25T15:00",
    "weather_code": 61,
    "condition": "slight_rain",
    "condition_en": "Slight rain",
    "condition_ru": "Небольшой дождь",
    "temperature": 12.4,
    "units": { "temperature": "°C", "wind_speed": "km/h", "precipitation": "mm" }
  }
}
```

- **`content`** — компактная сводка для человека и модели.
- **`structuredContent`** — те же данные как JSON, проверенные по `outputSchema` инструмента. Годится для расчётов и сравнений.

Особенности, важные для агента:

- **Единицы всегда возвращаются явно** в поле `units` — модель не должна угадывать.
- **`export_weather_summary_excel` добавляет второй блок в `content`** — встроенный ресурс с самим `.xlsx` (см. [выгрузку в Excel](#сохранение-сводок-и-выгрузка-в-excel)). `structuredContent` при этом остаётся обычным JSON без base64.
- **Код погоды WMO расшифровывается** (`weather_code: 61` → `condition: "slight_rain"`, `condition_en`, `condition_ru`).
- **`hourly` равен `null`**, если почасовой ряд не запрашивали: так модель отличает «не просили» от «просили, но пусто».
- **Ошибки приходят как `isError: true` с текстом**, а не как обрыв транспорта: упоминается вид ошибки, HTTP-статус, причина от upstream и то, временная она или нет. Пример:
  `Open-Meteo request failed [network]: Could not reach ensemble-api.open-meteo.com: fetch failed. This looks transient — retrying may succeed.`
- Серверные исключения логируются целиком, но наружу отдаётся общее сообщение — стектрейсы не утекают удалённому агенту.

## Подключение к ИИ-агенту

### Вариант A. Локально через stdio

Клиент сам запускает процесс сервера. Подходит для Claude Desktop, IDE-агентов и DSH.

```bash
npm install && npm run build && npm link   # кладёт bin `open-meteo-mcp` в PATH
```

Обобщённая конфигурация (формат `mcpServers`, который понимают большинство клиентов):

```json
{
  "mcpServers": {
    "open_meteo": {
      "command": "open-meteo-mcp",
      "args": ["--transport", "stdio"],
      "env": { "LOG_LEVEL": "warn" }
    }
  }
}
```

**Готовый оверлей для DSH** лежит в `deploy/dsh-mcp-overlay.example.yml`:

```bash
dsh web --patch "$PWD/deploy/dsh-mcp-overlay.example.yml"
```

DSH публикует инструменты как `mcp__<serverName>__<tool>`, то есть в модели они видны так:

```
mcp__open_meteo__geocode_location
mcp__open_meteo__get_current_weather
mcp__open_meteo__get_weather_forecast
mcp__open_meteo__get_air_quality
```

> `serverName` должен соответствовать `[A-Za-z0-9_-]{1,32}` — точки и пробелы недопустимы.

### Вариант B. Удалённо через Streamable HTTP (то, что нужно для VPS)

1. Разверните сервер (см. ниже) и получите URL вида `https://mcp.example.com/mcp`.
2. Подключите агента, передав заголовок `Authorization: Bearer <TOKEN>`.

Обобщённая конфигурация:

```json
{
  "mcpServers": {
    "open_meteo": {
      "type": "streamable-http",
      "url": "https://mcp.example.com/mcp",
      "headers": { "Authorization": "Bearer ${OPEN_METEO_MCP_TOKEN}" }
    }
  }
}
```

Для DSH — раскомментируйте «Option B» в `deploy/dsh-mcp-overlay.example.yml`; токен там читается из `process.env`, чтобы не хранить секрет в файле.

Проверка вручную, без агента:

```bash
curl -s https://mcp.example.com/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}'
```

## Выгрузка на VPS

### Docker Compose (рекомендуется)

```bash
cp .env.example .env
# обязательно заполните MCP_AUTH_TOKEN:
echo "MCP_AUTH_TOKEN=$(openssl rand -hex 32)" >> .env

docker compose up -d --build
docker compose logs -f
```

Порт публикуется **только на loopback** (`127.0.0.1:3000`) — снаружи его закрывает reverse proxy с TLS.

Контейнер запускается non-root, с `read_only` rootfs, `cap_drop: ALL` и `no-new-privileges`.

### systemd (без Docker)

```bash
sudo useradd --system --home /opt/open-meteo-mcp --shell /usr/sbin/nologin mcp
sudo mkdir -p /opt/open-meteo-mcp
# --exclude data и .env: с --delete rsync удаляет в приёмнике всё, чего нет
# среди источников, то есть историю сборщика и рабочий .env.
sudo rsync -a --delete --exclude data --exclude .env \
  dist/ node_modules/ package.json /opt/open-meteo-mcp/

sudo cp .env.example /etc/open-meteo-mcp.env
sudo chmod 600 /etc/open-meteo-mcp.env   # секреты — только root
sudo nano /etc/open-meteo-mcp.env        # впишите MCP_AUTH_TOKEN

sudo cp deploy/open-meteo-mcp.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now open-meteo-mcp
sudo systemctl status open-meteo-mcp
journalctl -u open-meteo-mcp -f
```

Юнит уже содержит хардненинг (`ProtectSystem=strict`, `PrivateTmp`, пустой `CapabilityBoundingSet` и т. д.).

> Обновление по **Docker**-схеме описано в `deploy/VPS-DEPLOYED.md`; там же про `--exclude data`, без которого `rsync --delete` снёс бы накопленную историю сборщика.

### nginx + TLS

Шаблон: `deploy/nginx.conf.example`.

Ключевые моменты, без которых не заработает:

- проброс заголовка `Authorization` (`proxy_set_header Authorization $http_authorization;`);
- `proxy_buffering off;` — иначе SSE-поток Streamable HTTP будет забуферен;
- `proxy_read_timeout` больше, чем `OPEN_METEO_TIMEOUT_MS × (OPEN_METEO_MAX_RETRIES + 1)`;
- редирект с HTTP на HTTPS, чтобы токен не ушёл в открытом виде.

Так как сервер по умолчанию **stateless**, привязка сессий в upstream не нужна — можно поднять несколько реплик.

## Тесты

```bash
npm test          # 170 тестов: unit + integration + watch + summary, полностью герметично
npm run typecheck
```

Интеграционные тесты поднимают **настоящий MCP-клиент** (`Client` + `InMemoryTransport`) и прогоняют реальный handshake, `tools/list`, валидацию аргументов и валидацию `structuredContent` по `outputSchema`. Upstream подменяется локальным моком (`test/mock-upstream.ts`), который повторяет контракт Open-Meteo: списки переменных, выравненные массивы, переключение единиц, пустой результат и конверт с ошибкой.

Что покрыто, помимо логики:

- все 12 инструментов зарегистрированы, у каждого есть title/description/annotations;
- **у каждого входного параметра есть описание** в сгенерированной JSON Schema;
- у каждого инструмента объявлен `outputSchema`;
- каждый инструмент возвращает и текст, и `structuredContent`;
- ошибки валидации и ошибки upstream превращаются в понятные `isError`-ответы;
- невалидные аргументы не доходят до сети;
- **переключение источника погоды**: тест собирает сервер с `OPEN_METEO_FORECAST_PATH=/v1/forecast` и без модели и проверяет, что запрос уходит именно на стандартный хост и без параметра `models` — то есть конфигурация для VPS покрыта тестом, а не только документацией;
- retry/таймаут/отмена, классы ошибок, разбор «сырого» JSON;
- **периодический сбор**: агрегация (тренд по половинам окна, период наблюдения, доли условий), retention и обрезка старых сэмплов, атомарная запись, устойчивость к битому JSON, транслитерация кириллицы в id, лимит watch-ей, персистентность реестра между запусками и понятная ошибка при недоступном каталоге данных;
- **сохранение сводок и Excel**: генератор `.xlsx` проверяется **собственным независимым читателем ZIP** (разбор central directory + CRC-32, посчитанный другой реализацией), нормализация строк (значения по умолчанию, округление, ISO-даты с смещением, лимиты `extra`), свёртка истории watch по суткам, лимиты сводок, устойчивость к испорченному `index.json`, обрезка старых выгрузок, встраивание файла в ответ и его совпадение по SHA-256 с копией на диске;
- **метрики не расходятся со схемой**: тест сверяет таблицу метрик с полями, описанными в JSON Schema инструмента `save_weather_summary`.

Дополнительно книга проверялась внешним читателем (`openpyxl`): листы, значения, кириллица, закреплённая шапка, автофильтр, ширины столбцов и числовые форматы читаются без ошибок. В репозитории этот шаг не автоматизирован — тесты остаются герметичными и без внешних зависимостей.

## Безопасность

- **Публичный bind без токена запрещён.** Сервер падает при старте, если `MCP_HOST` не loopback и не задан `MCP_AUTH_TOKEN` (обойти можно только явным `MCP_ALLOW_UNAUTHENTICATED=true`).
- Токен сравнивается **за постоянное время** (`timingSafeEqual`) — его нельзя подобрать по таймингам.
- Токен принимается **только в заголовке** `Authorization`, не в query-параметре (query попадает в логи прокси).
- Аннотации честные: инструменты чтения помечены `readOnlyHint: true`, сохраняющие и выгружающие — `false` (они пишут файлы), а `destructiveHint: true` стоит только у `delete_weather_watch`. Перезапись сводки требует явного `replace: true`, поэтому случайный повторный вызов ничего не стирает.
- Имена файлов выгрузки санитизируются, а `dataset_id` не может содержать `/` — записать файл вне каталога выгрузок через аргументы инструмента нельзя.
- Наружу не отдаются стектрейсы и внутренние адреса.
- Ограничение размера тела запроса; на VPS дополнительно ограничьте `client_max_body_size` в nginx.
- Логи идут в stderr, stdout свободен для протокола — случайный `console.log` не порвёт MCP-сессию.

Что стоит сделать перед публикацией в интернет:

1. TLS обязателен — иначе токен уходит открытым текстом.
2. Ограничьте частоту на уровне прокси: бесплатный тариф Open-Meteo имеет лимиты, а `/mcp` без rate limit — удобная точка для абьюза.
3. Ротируйте `MCP_AUTH_TOKEN` и не коммитьте `.env` (он в `.gitignore`).
4. `/healthz` намеренно без аутентификации — закройте его от интернета средствами прокси (пример в `nginx.conf.example`).

## Известные ограничения

- **Геокодирование работает только по названиям.** Улицы, индексы и достопримечательности не находятся — это ограничение самого Open-Meteo.
- **Данные — это выход модели, а не показания станции.** Погода обновляется примерно раз в 15 минут, качество воздуха — раз в час; значения могут слегка отличаться от уличного термометра.
- **`precipitation_probability` равен `null` в конфигурации по умолчанию** (ансамблевый хост его не отдаёт). Переключение на стандартный хост возвращает это поле — см. [Источник данных](#источник-данных).
- **`api.open-meteo.com` может быть недоступен из вашей сети.** Это не ошибка сервера: дефолт настроен на доступный хост. На VPS имеет смысл проверить `curl -sS -o /dev/null -w '%{http_code}\n' --max-time 10 'https://api.open-meteo.com/v1/forecast?latitude=55.75&longitude=37.61&current=temperature_2m'` и, если он отвечает, переключиться на конфигурацию B.
- **Прогноз дальше ~7 дней — это тренд**, а не точное предсказание. Сервер отдаёт до 16 дней, но в описании инструмента это оговорено явно.
- **Регион `stateful`** хранит сессии в памяти процесса: при рестарте они теряются, и клиент должен инициализироваться заново. Для VPS по умолчанию используется `stateless`.
- **`include_hourly` на 16 дней** даёт ~384 объекта — большой ответ; включайте осознанно. На ансамблевом хосте ответ дополнительно содержит данные всех членов ансамбля, поэтому он заметно тяжелее (~500 КБ против ~200 КБ на стандартном хосте).
- **Один экземпляр сборщика.** Сборщик запускается в каждом процессе. Если поднять несколько реплик контейнера с общим каталогом данных, они будут опрашивать погоду независимо и дублировать сэмплы. Для горизонтального масштабирования вынесите сбор в отдельный процесс.
- **Молодой watch отдаёт короткий период.** Через час после регистрации отчёт за 24 ч вернёт ~1 час наблюдений — это норма, а не ошибка. `observed_span_minutes` показывает фактический период; агрегаты считаются по имеющимся сэмплам.
- **Сборщик не переживает недоступность upstream молча.** Если опрос падает, сэмпл не пишется, а отчёт показывает предупреждение с числом подряд идущих ошибок и их текстом — устаревшие данные не выдаются за свежие.
- **Сводки не удаляются инструментом.** `replace: true` перезаписывает сводку, но убрать её совсем можно только на хосте (`rm data/summaries/<id>.json`). Это осознанно: удаление данных заслуживает отдельного явного действия, а не «заодно» вызванного инструмента.
- **Excel-выгрузка без формул и диаграмм.** Генератор `src/xlsx/` пишет значения, числовые форматы, ширины, закреплённую шапку и автофильтр — этого достаточно для таблицы данных, но графики и формулы в неё не встроены.
- **Большая книга не встраивается в ответ.** Свыше `SUMMARY_MAX_INLINE_BYTES` (8 МиБ) файл только пишется на диск, а в ответе остаётся путь: на удалённом HTTP-подключении забрать его оттуда нельзя, поэтому лимит стоит поднять или уменьшить саму сводку.
- **Лимит запросов.** У бесплатного тарифа Open-Meteo есть поминутное ограничение; при его превышении сервер вернёт `rate_limited` с пометкой, что запрос временный. При частых вызовах стоит добавить кэширование перед сервером.
